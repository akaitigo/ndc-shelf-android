# ADR 0001: 棚内順序にfractional order keyを使う

- Status: Accepted
- Date: 2026-07-26
- Related: #21

## Context

段内の本を連番で管理すると、先頭や途中へ1冊挿入するたびに後続行の全面更新が必要になります。大規模な蔵書では書き込み時間が増え、将来の複数端末同期でも無関係な行同士が競合します。一方、浮動小数点の中間値は反復編集で精度を失い、端末や実装間の再現性も弱くなります。

## Decision

`OwnedCopy.shelfOrderKey`へ、可変長byte列を小文字16進数で表したfractional order keyを保存します。挿入時は左右キーをbyte単位で比較し、最初に空いている中間値を生成します。中間値以降へcopy IDのSHA-256先頭8 byteを付け、異なる端末が同じ区間へ同時挿入してもキーが衝突しにくくします。

通常の挿入・移動で更新するのは対象copy 1行だけです。並びは`shelfOrderKey`、`addedAt`、`copyId`の順で安定化します。copy IDも最終tie-breakerになるため、極めて低確率のhash衝突や同期途中でも順序とデータを失いません。

v2からv3へのMigrationでは、階層へ割り当て済みのcopyだけに`addedAt`とcopy IDから安定した初期キーを設定します。旧バックアップ等でキーが欠ける場合は、最初の並べ替え操作時にその段だけを修復します。

## Consequences

- 途中挿入と左右移動は棚の冊数に依存しない局所書き込みになる。
- 同期競合時も同位置のcopyを決定的に表示できる。
- 同じ狭い区間への反復挿入でキーは長くなる。バックアップの文字列上限内で検証し、将来計測で問題になった場合だけ段単位の明示的な圧縮処理を追加する。
- キーは内部実装であり、JSON/CSVには公開しない。完全バックアップでは保持する。

## Acceptance Evidence

- 先頭・中間・末尾と同時挿入相当の単体テスト
- 10,000件を既存キーの全面更新なしで生成する性能テスト
- Room Migration、Repositoryの位置指定・左右移動、完全バックアップの往復テスト
