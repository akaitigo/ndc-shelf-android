# v0.4 ロールバック手順

## 原則

Androidは通常、低い`versionCode`への上書きdowngradeを許可しない。v0.4配布後に問題が判明してもv0.3 APKを再配布せず、v0.4 codebaseからより大きい`versionCode`のhotfixを作り、データを保持してroll forwardする。

Room v8からv11とbackup形式版9から12はseries、work group、watch、release candidateを追加する。アプリdata削除、`fallbackToDestructiveMigration`、古いschemaへのdowngradeを復旧策にしない。

## 配布前

1. 段階配布率を0%へ戻し、新規配布を停止する。
2. v0.3とv0.4のrelease commit、同一署名artifact、mapping、SBOM、SHA-256を保持する。
3. 匿名fixtureで問題を再現し、実在する蔵書、シリーズ名、通知内容をIssueへ添付しない。
4. data loss、意図しない外部送信、秘密情報を含む場合は公開Issueを避け、Private Vulnerability Reportingで扱う。

## 配布後

1. ストアの段階配布を停止する。install済みアプリを遠隔downgradeしない。
2. 影響をseries表示、関連解除、Migration、backup、background通信、通知に分類する。
3. 原因を匿名fixtureで再現し、既存Room v11 schemaを維持した最小hotfixを作る。
4. 修正版でRoom v7→v11、影響を受けるbackup形式、OFF時無通信、通知重複防止を再検証する。
5. `versionCode`を増やしたhotfixを同じ署名で段階配布する。

## 利用者データの復旧

- Migration障害: 失敗端末のdata削除を案内せず、旧版DBからの明示的Migrationと回帰fixtureを追加する。
- 誤ったseries所属: Membershipまたはwork groupだけを解除し、Work、Edition、OwnedCopyを変更しない。
- watch・通知障害: periodic workを停止できるhotfixを優先し、保存済み候補は削除せず再評価する。
- backup障害: restore前の自動退避backupを保持し、checksum検証なしにarchiveを編集・展開しない。
- 外部送信障害: watchをfail closedでOFFにし、送信対象・時刻・原因をprivacy incidentとして記録する。

## 受け入れ条件

- rollback判断者、配布停止時刻、影響version、hotfix責任者、artifact SHA-256をincident記録へ残す。
- 現在DBを削除せず、復旧不能な操作の前に検証済みbackupを確保する。
- hotfixでも候補と確定事実の境界、OFF時無通信、既存蔵書保持を自動テストする。
- 通常のbranch protection、review、CI、段階配布を通し、緊急性を理由に検証をskipしない。
