# v0.2 ロールバック手順

## 原則

Androidは通常、低い`versionCode`への上書きdowngradeを許可しない。v0.2配布後に問題が判明しても、v0.1.2 APKの再配布をrollback手段にしない。v0.2のcodebaseから修正版を作り、より大きい`versionCode`でroll forwardする。

## 配布前

1. 段階配布率を0%へ戻し、新規配布を停止する。
2. release commit、署名済みartifact、mapping、SBOM、SHA-256を保持する。
3. 匿名fixtureで問題を再現し、実在する蔵書や利用者のbackupをIssueへ添付しない。
4. data lossまたは秘密情報を含む場合は公開Issueを避け、Private Vulnerability Reportingで扱う。

## 配布後

1. 対象のGitHub Releaseをpre-releaseへ戻し、リリースノート冒頭へ警告を追記する。既に配布済みのAPKは回収できないため、告知が唯一の手段である。遠隔でのdowngradeは行わない。
2. DB schemaをさらに変更せず、原因を再現して修正版を作る。破壊的migrationを使わない。
3. 修正版で既存v0.2 DB、v0.1.2 DB、形式版1／2 backupを検証する。
4. `versionCode`を増やしたhotfixを同じ署名で配布する。
5. restore不具合では自動退避backupを保持し、利用者へアプリdata削除や再installを安易に案内しない。

## 利用者データの復旧

- JSON／CSV import障害: 現在DBを維持し、修正版で元ファイルを再検証する。CSVは完全backupではない。
- 完全restore障害: `noBackupFilesDir/restore-backups`の自動退避を優先し、checksum検証なしに展開・編集しない。
- OS端末間転送障害: 手動完全backupを案内し、クラウドbackupを一時的に有効化しない。
- schema障害: 影響版からの明示的Room migrationとfixture testを追加し、`fallbackToDestructiveMigration`を使わない。

## 受け入れ条件

- rollback判断者、停止操作、hotfix責任者、artifact SHA-256をincident記録へ残す。
- 現在DBを削除せず、復旧不能な操作の前に整合性のあるbackupを確保する。
- hotfixも通常のbranch protection、review、CI、段階配布を通す。
