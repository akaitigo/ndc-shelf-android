# v0.4 シリーズ管理リリースチェックリスト

## 判定

**状態: BLOCKED（実機証跡と依存release確定待ち）**

自動検証はPull Requestごとに実行する。release candidateは`versionCode = 6`、`versionName = "0.4.0"`とする。以下のゲートを全て証跡付きで完了するまで、tag作成と配布を行わない。既存蔵書の欠落、候補の無断確定、通知OFF時の通信、重複通知が1件でもあればreleaseを停止してIssue化する。

## 対象

- 更新元: v0.3 release commit（`versionCode = 5`、Room v7。公開artifactとSHAは未確定）
- 更新先: v0.4 release candidate commit（`versionCode = 6`、Room v11。検証時にSHAを記録）
- backup: 形式版12。v0.4でseries、work group、watch、release candidateを含む
- fixture: `V04SeriesReleaseTest`と`AppDatabaseMigrationTest`内の匿名データ
- 禁止データ: 実在する個人蔵書、個人名、自宅の置き場所、private URI、実在シリーズ名を含むログ

v0.3のrelease commitと同一署名artifactが確定するまでは、更新install試験を完了扱いにしない。v0.2またはv0.1.2から直接更新する場合も全Room Migrationを通るが、公開経路ごとの更新試験を省略しない。

## 既知制約

- title解析とNDL書誌は候補であり、自動的に確定済みseries事実へ昇格しない。
- 欠巻はユーザーが確定した明示的な本編Membershipのうち未所有のものだけを示す。未登録番号の存在や刊行済みであることは断定しない。
- 最新所有巻は保存済みの並び順で最後の所有巻であり、外部の最新刊を意味しない。
- 新刊候補確認は明示的opt-inで、成功後は7日間隔を空ける。一時障害時はWorkManagerが再試行し、発売日、網羅性、在庫を保証しない。
- series統合、cloud同期、複数端末同期はv0.4の対象外である。

## 最終release操作

全ゲート完了後に別PRで次を実行する。

1. v0.3更新元artifact、`versionCode = 6`、全証跡を再確認する。6が配布済みなら未使用のより大きい値へ上げ、更新試験を再実施する。
2. `CHANGELOG.md`の`Unreleased`を日付付き`0.4.0`へ確定する。
3. signed release build、mapping、SBOM、commit SHA、artifact SHA-256を保存する。
4. tag `v0.4.0`をrelease commitへ付け、段階配布する。
5. crash、ANR、Migration failure、data loss、通知・通信の報告を監視する。保護設定や必須checkを回避しない。
