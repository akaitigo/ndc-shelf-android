# v0.3 ロールバック手順

## 原則

Androidは低い`versionCode`への通常downgradeを許可しないため、v0.2 APKの再配布やapp data削除をrollback手段にしません。配布停止後、v0.3 codebaseから`versionCode > 5`の修正版をroll forwardします。

## 配布前

1. v0.2とv0.3のrelease commit、署名済みartifact、SHA-256、署名証明書fingerprint、mapping、SBOMを保管する。
2. 匿名fixtureでv0.2→v0.3 Migration、完全backup、複数copy、棚順、購入状態、scan取消を再確認する。
3. 段階配布率、停止権限、hotfix責任者、連絡経路を記録する。
4. 実在蔵書やバーコード画像をログ、Issue、crash添付へ含めない。data lossまたは秘密情報はPrivate Vulnerability Reportingで扱う。

## 配布後

1. crash、ANR、data loss、Migration失敗、scan失敗率の閾値超過で段階配布を停止する。
2. install済み端末を遠隔downgradeせず、現在DBを削除しない。
3. 影響DB版と操作を匿名fixtureで再現し、破壊的Migrationや`fallbackToDestructiveMigration`を使わない修正版を作る。
4. 修正版をv0.2 DBとv0.3 DBの両方から検証し、より大きいversionCodeで通常CI・review・段階配布を通す。
5. 修復不能な可能性があれば、書込み機能を止めて完全backupの保全を先に案内する。

## データ別の復旧

- 棚階層・順序: 旧`location`文字列を保持し、`tierId`と`sortOrderKey`だけを安全に再構築する。copyを削除して作り直さない。
- 複数copy: `copyId`ごとの表示名、状態、追加時刻を保持し、ISBN単位へ集約しない。
- 購入状態: WishlistとOwnedCopyを同時に作らず、単一transactionで再適用する。
- scan取消: snapshot hashが一致しないcopyを削除せず、競合として手動確認へ送る。
- 完全backup: checksumと自動退避backupを優先し、手編集したarchiveを復元しない。

## 受け入れ条件

- 配布停止判断者、hotfix責任者、影響版、原因、artifact SHA-256をincident記録へ残す。
- 現在DBと自動退避backupを削除せず、v0.2・v0.3双方から修正版へ移行できる。
- hotfixもbranch protection、review、CI、署名、段階配布を回避しない。
