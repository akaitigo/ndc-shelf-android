# 蔵書検索の性能予算

## 問題

`observeLibrary()`は全JOIN行を返し、`LibraryScreen`は検索入力ごとに全件の文字列を走査します。処理はComposeの再コンポーズ中に行われるため、件数に比例して入力遅延とメモリ使用量が増えます。

## 代表データ

`tools/benchmark_library_search.main.kts`は次の分布で1,000、5,000、20,000冊を生成します。

- タイトルは97冊ごとに検索語「郷土」を含む
- 著者431種類、部屋8、棚32、段5、読書状態4種類を均等に割り当てる
- ISBN、NDC、追加時刻は各行で異なる
- 検索対象はタイトル、著者、ISBN、NDC、場所、読書状態とする

## 現状計測

2026-07-27にLinux/JDK 17上で、25回の中央値を計測しました。値はクライアント側の部分一致検索とタイトル並べ替えだけで、RoomのJOIN、行変換、Compose描画は含みません。

## 性能予算

Pixel 7相当の基準端末とAPI 35以上のrelease相当ビルドで次を満たします。

| 指標 | 5,000冊 | 20,000冊 |
| --- | ---: | ---: |
| 絞り込み確定から結果表示までのp95 | 150 ms以下 | 250 ms以下 |
| 入力停止から結果表示までのp95（debounce込み） | 350 ms以下 | 500 ms以下 |
| 条件なしの初期取得p95 | 200 ms以下 | 750 ms以下 |
| 本棚画面による追加ヒープ | 16 MiB以下 | 32 MiB以下 |
| 一覧スクロールのフレームp95 | 16.7 ms以下 | 16.7 ms以下 |

JVM/Robolectric回帰テストは共有CIのばらつきを考慮し、1,000、5,000、20,000冊の検索結果・順序・キャンセルを検証します。時間の合否は基準端末のMacrobenchmarkで判定し、JVMの絶対時間だけでCIを不安定化させません。

## Room実装後の計測

Robolectric上のRoom実クエリで、JOIN、行変換、結果List生成までを計測しました。共有CIで絶対時間を厳格判定すると不安定になるため、回帰テストの上限は5秒とし、次の値は比較用の観測値として記録します。

| 冊数 | 「郷土」絞り込み | 条件なし初期取得 | 結果件数 |
| ---: | ---: | ---: | ---: |
| 1,000 | 22 ms | 57 ms | 11 |
| 5,000 | 33 ms | 151 ms | 52 |
| 20,000 | 82 ms | 585 ms | 207 |

## 採用判断

- Room側で検索条件と並び順を適用し、Compose側の全件線形検索を廃止する
- ViewModelで入力を250ms debounceし、`flatMapLatest`で古い検索をキャンセルする
- 検索条件と結果を同じ状態として公開し、条件が一致しない古い結果は表示しない
- 全件Flowは本棚または分析画面が表示されている間だけ購読し、データ画面は集計クエリだけを使う
- タイトル、著者、ISBN、NDC、場所は前方一致だけでなく部分一致が必要なため、通常のB-tree索引を検索用途には追加しない
- 20,000冊の絞り込みが82msで予算内のため、読書状態専用索引と追加の並べ替え索引は現時点では追加しない
- FTSは日本語トークナイズと同期用テーブルの書込みコストが増えるため、20,000冊で性能予算を超える実測が出るまで導入しない
- Paging 3はメモリ効率に有効だが、5,000冊の初期取得151msと検索33msが予算内で、詳細・棚編集が同版コピーと隣接本を同時に必要とするため今回は追加しない。基準端末で20,000冊時の追加ヒープが32MiBを超えた場合に再評価する

Android公式の[Room DAOガイド](https://developer.android.com/training/data-storage/room/accessing-data)ではDAOがPaging 3の`PagingSource`を直接返せること、[Paging 3概要](https://developer.android.com/topic/libraries/architecture/paging/v3-overview)では大規模データのメモリ効率、リクエスト重複排除、Flow連携が示されています。

## リスクとロールバック

- 詳細画面やコピー編集で同じ版のコピーと棚の隣接本を欠落させないよう、詳細表示中は選択Editionと棚配置済みコピーを取得する
- DB更新でRoomのObservable Queryが再実行された場合も、検索条件と並び順を維持する
- 基準端末で入力p95が予算を超える場合は、FTS導入前にSQLプラン、不要なJOIN、ページサイズを再計測する
- 回帰時は従来の`observeLibrary()`を削除せずInsights・エクスポート用のスナップショット取得へ限定して戻せるようにする
